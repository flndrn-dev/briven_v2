# Deploy Briven — agent runbook

Read this before any deploy. It is the only deploy procedure. Do not guess from older notes that mention the France machine.

Two different GitHub projects ship to one Dokploy project. They are not the same codebase and they must not be deployed as one stack.

| What | GitHub | What a push to `main` does |
|---|---|---|
| Website, dashboard, and the API those pages call | `flndrn-dev/briven-website` (private) | Dokploy rebuilds the live site on the Briven server |
| Database engine (the v2 storage engine) | `flndrn-dev/briven_v2` (this repo when you are in it) | Saves the engine code only. It does **not** publish a public database |

Public site: `https://briven.tech`  
Control panel: `https://admin.loowii.com`  
Briven server: `187.77.183.190` (Dokploy name `KVM2`, server id `kvm2-server`)

`briven.tech`, `www.briven.tech`, and `api.briven.tech` already point at that server. Do not move those names back to the France machine.

## Never do this

- Never write a password, API key, or private key into this file, a commit, a log, or a chat reply.
- Never deploy `docker-compose/docker-compose.yml` from `briven_v2`. That file is a practice stack. It contains the sample password `password` and publishes storage ports. Putting it on the public server would leave a practice database on the internet.
- Never change the Dokploy compose named `briven-france` (id `Qp9Zg2JRqbJ6onE1_n6OO`). That one still sits on the old France machine `187.124.64.116` and is not what `briven.tech` uses.
- Never start a second website deploy while one is already `running`. A second full build can exhaust the server.
- Never set the website compose's server with `compose.update`. Dokploy ignores `serverId` on update. A service is born on a server and stays there. The live website service was created on `kvm2-server`. Do not recreate it.
- Never point the engine at `briven.tech`, and never point the website at the engine. They stay separate until flndrn says the hosted engine is ready.

Repo: `https://github.com/flndrn-dev/briven-website.git`  
Branch: `main`

Compose name: `briven-website`  
Compose id: `LykAyuz6qInYZe37wIMLp`  
App folder on the server: `briven-website-kvm2-jji23y`  
Compose file: `infra/dokploy/compose.dokploy.yml`  
GitHub connection id: `7Yb-urnCtHiEgC4cfNWEA`  
Owner / repo / branch: `flndrn-dev` / `briven-website` / `main`  
Auto-deploy: **on**. A push to `main` starts the deploy by itself.

That one compose builds the site, the API, the docs, and their databases together. Do not make a second Dokploy app for "just the website" or "just the API".

### Save and send

From a checkout of `briven-website`:

```bash
git status
git add <only the files you changed>
git commit -m "why this change exists, in one line"
git push origin HEAD:main
```

Push only when the work is one finished chunk. Every push rebuilds the whole stack.

If `git push` says the GitHub login failed, stop. Do not invent a token. Ask flndrn.

### If the push did not start a deploy

Sign in to Dokploy with the panel login flndrn keeps outside git. Then:

```bash
POST https://admin.loowii.com/api/trpc/compose.deploy
Content-Type: application/json

{"json":{"composeId":"LykAyuz6qInYZe37wIMLp","title":"Deploy Briven website"}}
```

Call that once. If the compose status is already `running`, do not call it.

### Watch it

On the Briven server (key `~/.ssh/briven_v2_server`, not `briven_kvm2`):

```bash
ssh -i ~/.ssh/briven_v2_server -o IdentitiesOnly=yes root@187.77.183.190
ls -lt /etc/dokploy/logs/briven-website-kvm2-jji23y | head
```

Read the newest log. Failure looks like `Error occurred`. Success is the compose status `done` and the site answering.

### Prove it is live

```bash
curl -sI https://briven.tech | head
curl -sS https://api.briven.tech/ready
```

A page that loads, and a ready check that succeeds, are the proof. "Deploy finished" in the panel is not enough.
